# 프로젝트 방향성 회의록 — 2026-08-30

## 1. 문서 지위

이 문서는 제출 전 프로젝트의 큰 방향, 우선순위, 병렬 작업 구조에 관한 사용자와
Codex의 합의를 기록한다.

- 세부 데이터 계약, 컬럼 binding, Registry 항목 또는 테스트 질문을 미리 확정하지 않는다.
- 이 기록만으로 `ARCHITECTURE.md`, `IMPLEMENTATION_PLAN.md`, `contracts/`의 상태를
  변경하지 않는다.
- 각 작업은 필요한 시점에 필요한 범위만 결정하고 구현한다.
- 세부 작업 중 전체 방향이나 공유 계약에 영향을 주는 사안만 다시 회의로 가져온다.

## 2. 현재 상태에 대한 공통 인식

- Clean migration과 원본 custody 기반은 마련됐다.
- 0-A HCX 실험은 모델이 값, 조건, 정렬, 관계 방향, 비교 요구를 안정적으로 보존하지
  못할 수 있음을 확인했다.
- 0-B는 로컬 API transport와 응답 envelope까지만 검증됐고 NCP 원격 배포는 남아 있다.
- Runtime View retrieval은 synthetic Registry 기반 실험까지 진행됐다.
- 공식 Excel과 holdings normalized v1에 대한 read-only discovery는 수행됐다.
- 공식 Excel에서 실제 질의 결과와 Evidence가 생성되는 end-to-end 경로는 아직 없다.
- Gold, 실제 Coverage 실행 정책, 실제 Registry, holdings v2, 전체 통합과 리허설은
  아직 완료되지 않았다.

## 3. 실데이터 조사에서 확인된 방향 수정 근거

- 파일이나 컬럼의 존재만으로 관련 질문을 실제 지원할 수 있다고 볼 수 없다.
- 일부 지표는 원천 필드가 없고, 일부는 관측 모집단에서만 질의할 수 있다.
- 상품군 간 같은 이름의 지표도 의미, 기간, 단위, 통화, freshness가 같다고 확정할
  근거가 부족할 수 있다.
- 상품 행과 source-row grain이 일치하지 않는 상품군이 있다.
- holdings는 단순 JOIN 시 관계 팽창과 중복이 발생하며 identifier scheme도 상품군별로
  다르다.
- 공모펀드 holdings의 security 관계는 식별자와 weight 공백 때문에 ETF와 같은 방식으로
  바로 처리할 수 없다.

따라서 실제 데이터 검증을 Stage 5까지 미루지 않는다. 다만 전체 데이터 계약을 앞서
만드는 대신, 각 capability 구현 시점에 필요한 데이터 의미와 계약만 확인한다.

## 4. 제출물의 큰 목표

현재 확보한 데이터 안에서 도메인적으로 자연스럽고 데이터 의미가 확인된 조회를 가능한
한 폭넓게 지원한다.

- 상품 조건 검색
- 다중 조건 필터
- 정렬과 상위·하위 조회
- 개수와 집계
- 상품 간 비교
- 기간·지표 기반 조회
- 데이터가 허용하는 상품과 보유종목의 양방향 관계 조회
- Evidence, 기준일, 모집단을 포함한 답변

실제 사용 의미 없이 평가 복잡성만 높이는 중첩 질의나 데이터가 지원하지 않는 관계를
억지로 결합한 질의는 목표로 삼지 않는다.

예시 질문을 만들 필요가 생기면 test purpose, capability under test, 질문 구조,
expected invariant를 먼저 제시하고 사용자 검수를 받은 뒤 사용한다. 예시 질문이나 기존
평가 질문 문자열을 제품 사양이나 런타임 분기로 사용하지 않는다.

## 5. 필요한 때 필요한 만큼 결정하는 원칙

- 전체 질문 세트를 미리 분류하지 않는다.
- 전체 상품군 데이터 계약을 미리 확정하지 않는다.
- 미래 범위의 Registry를 선제적으로 작성하지 않는다.
- 외부 데이터 계약은 실제로 필요한 capability가 등장할 때 작성한다.
- `supported`, `partial`, `unsupported`, `unresolved` 판정은 실제 실행이나 최종 claim에
  필요할 때 적용한다.
- semantic mapping이나 compiler 자체를 검증하는 질문에는 데이터 부재만으로 동일한
  판정을 강제하지 않는다.

## 6. 병렬 작업 구조

메인 회의 채팅을 조정 창구로 유지하고 다음 작업을 별도 채팅과 가능하면 독립
worktree에서 병렬로 진행한다.

### A. 공식 데이터 실행 기반

- 현재 확보한 공식 데이터를 실행 가능한 파생 데이터에 연결한다.
- 상품군별 조회 범위를 넓히고, 필요한 시점에 grain, identifier, field 의미를 결정한다.
- 질문 해석이나 HCX 계약은 담당하지 않는다.

### B. 질문 해석과 결정적 compiler

- Runtime View, HCX 요구사항 구조화, requirement 검증과 결정적 실행 계획을 담당한다.
- 데이터 의미를 임의로 추측하지 않고 데이터 작업이 확인한 binding만 사용한다.

### C. Product 조회와 Evidence

- 상품 filter, order, count, aggregate, compare와 Evidence 생성을 담당한다.
- 국내 ETF를 첫 실제 실행 기준선으로 사용하되 다른 상품군의 작업을 막는 선행조건으로
  만들지 않는다.

### D. Holdings와 관계 조회

- Product/class, Portfolio, Security 관계와 양방향 holdings 조회를 담당한다.
- 국내·해외 ETF 관계 작업은 공모펀드의 미확정 관계를 기다리지 않고 진행한다.
- 공모펀드 product metric은 계속 진행하고, holdings security 관계는 별도 경로로
  해결한다. 이는 기능 포기가 아니라 일정 의존성 분리다.

### E. NCP 배포·통합·검증

- NCP 원격 배포, `/answer` API, 트랙 간 통합, latency, 오류, 회귀와 제출 리허설을
  담당한다.
- 첫날부터 배포 기반을 진행하고 다른 트랙의 결과가 나오는 즉시 연결한다.

## 7. 우선순위와 일정 원칙

우선순위는 다음과 같다.

1. 현재 수집된 공식 데이터 활용 극대화
2. 공식 데이터 기반 end-to-end 질의와 Evidence 완성
3. holdings 관계 기능
4. NCP 통합과 안정화
5. 시간이 남으면 외부 데이터 보강

4일 운영의 큰 흐름은 다음과 같다.

- 1일차: 모든 병렬 트랙 착수와 기반 작업
- 2일차: 상품군 확장과 첫 실제 통합
- 3일차: 공식 데이터 기반 capability 폭 확대와 통합 보완
- 4일차: 사용자 승인 질문을 이용한 전체 리허설, 오류 수정, 최종 배포

막히는 작업을 사전에 포기하거나 제거하는 계획은 두지 않는다. blocker가 생기면 메인
회의로 즉시 반환하고 병렬 작업을 재배치해 해결을 계속한다. 다만 데이터가 지원하지 않는
주장을 성공한 것처럼 만들거나 근거 없는 답을 생성하지는 않는다.

## 8. 세부 작업에 위임하는 사항

각 병렬 작업은 승인된 큰 경계 안에서 다음을 자율적으로 결정한다.

- 사용할 세부 컬럼과 내부 모듈 구조
- 해당 capability에 필요한 최소 데이터 계약
- queryable universe 계산과 테스트 방법
- Registry binding과 중복 처리
- 구체적인 구현 순서와 수용 기준

다음 사항은 작업자가 임의로 확정하지 않고 메인 회의로 반환한다.

- 전체 아키텍처 변경
- 확인되지 않은 데이터 의미나 단위의 확정
- 공유 Coverage 정책 또는 공유 계약 변경
- 다른 병렬 트랙과의 인터페이스 충돌
- 제출 범위의 확대 또는 축소
- 외부 데이터 사용이 전체 방향에 영향을 주는 경우

## 9. 아직 확정하지 않은 사항

- 각 병렬 채팅의 실제 생성과 담당 배정
- 첫 구현 capability의 정확한 필드 범위
- 외부 데이터가 처음 필요한 capability와 source
- holdings를 제출 시점에 어느 깊이까지 통합할지
- 세부 Registry binding과 entity-resolution 규칙
- 정본 문서의 구체적인 수정 시점과 문구

이 항목들은 실제 작업에 필요해질 때 결정한다.

## 10. 회의 종료

이 회의는 2026-08-30 종료됐다.

회의에서 확정된 것은 제출물의 큰 목표, 필요한 시점에 필요한 만큼 결정하는 원칙,
A~E 병렬 작업 구조, 공식 데이터 우선순위와 4일 통합 흐름이다. 세부 데이터 계약,
필드 binding, 예시 질문, 외부 데이터 source와 구현 방식은 각 작업에서 필요해질 때
결정한다.

회의 종료 후 사용자 승인에 따라 합의를 `IMPLEMENTATION_PLAN.md`, `CONTEXT.md`,
`AGENTS.md`에 반영했다. `ARCHITECTURE.md`, `QUESTION_STRUCTURE.md`와
`contracts/EVALUATION_API.md`는 이번 합의로 변경하지 않았다.
